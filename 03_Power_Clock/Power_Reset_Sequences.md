## 1. 复位、上电与使能不是同一动作

Reset（复位）把指定逻辑置于规定状态，不等于切断供电；Enable（使能）控制某项功能，也不一定释放复位。
Assert Reset 表示让复位有效，Deassert 表示解除复位；物理高低电平由极性及软件接口决定。复位可以是外部引脚、片上控制器、软件命令或多个层级。
Linux reset controller API 还区分独占/共享等使用模型，不能照抄一个 assert/deassert 调用就假定板上 Sensor 引脚已改变。[Linux v6.8 Reset API](https://www.kernel.org/doc/html/v6.8/driver-api/reset.html)

## 2. 用依赖图，不背万能时序

先从手册收集：电源允许范围与先后、复位有效条件、参考时钟要求、启动等待、首次总线访问及开流条件。
以下是假设某器件要求的逻辑依赖，不是实际 Sensor 推荐序列：

```text
目标供电达到要求 ─┐
所需参考时钟有效 ─┼→ 按要求解除复位 → 等待器件启动条件 → 首次寄存器访问
复位已保持足够久 ─┘
```

图只表达依赖，不规定三项准备可以任意并行，也不确定 AVDD/DVDD/I/O 电源彼此顺序。实际器件可能要求参考时钟先于或晚于某一步，应完全按其资料调整。
延时要说明从哪个事件计时、为何等待、何时算满足。等待可以由时序下限、稳定状态或握手决定；只增加某个 sleep 不能证明根因和正确性。

## 3. 软件动作与物理证据成对记录

| 阶段 | 软件要做什么 | 观测什么 |
|---|---|---|
| 资源准备 | 获取正确电源/时钟/复位/引脚资源，检查错误 | 资源绑定、所有者、默认状态 |
| 建立条件 | 按依赖启用，处理失败 | 负载端电压、时钟和复位的共同时间线 |
| 首次访问 | 选择目标与格式，等待允许访问的时机 | 总线事务、应答、返回长度、真实 ID |
| 功能运行 | 配置采集及接收/内存通路，确认本轮结果 | 状态、图像输出、完成和数据有效性 |
| 退出/恢复 | 协调消费者和在途访问，按协议停机 | 是否仍有 DMA/总线访问、状态是否保留或需重建 |

Linux Camera Sensor 文档把时钟、电源与运行时 PM 作为驱动资源协同管理，但具体启动和关闭动作仍来自器件/平台要求。[Linux v6.8 Sensor 资源管理](https://www.kernel.org/doc/html/v6.8/driver-api/media/camera-sensor.html)

## 4. 首次访问需要的不止 Sensor 电源

还要检查控制器供电/时钟/复位、引脚复用、I/O 供电与电平、总线路径、访问权限、目标地址及事务格式。
存在 I2C 上拉时还须核对上拉电源和两端掉电行为。I/O 上仍有信号不证明核心供电正常；也不能在缺少容限依据时向掉电器件持续施加信号。
时钟能否在复位有效期间存在、哪一步允许 I/O 操作，都属于具体器件约束。

## 5. 失败回滚与关闭路径

每次资源获取/使能都应知道是否由自己持有、能否共享、失败后要释放哪些引用。回滚只撤销已成功取得且应由本次归还的资源。
关闭路径要先确保相关在途工作已按契约结束或停止，不能在 DMA 仍访问内存或总线事务未结束时随意关掉其依赖。
“掉电顺序一定等于上电的反序”不是通用规则：器件可能有停流、复位、I/O、放电和延时的独立要求。休眠恢复是否等同于冷启动，也要按保留状态区分。

## 6. 模拟问题：第一次读 ID 偶尔失败，重试成功

类型：模拟，无实测根因。候选原因包括访问太早、控制器/引脚准备晚、供电动态变化、总线竞争或事务格式错误，不把“重试有效”直接解释为应增加固定延时。
验证：对齐供电达到条件、MCLK 有效、复位解除、首个 START、应答及错误返回的时间，必要时区分冷启动与恢复；使用手册明确的时间参照和状态。
定位后再修正依赖、等待依据、资源管理或事务。未验证前不宣布某个 rail 或固定延时为根因/修复。
