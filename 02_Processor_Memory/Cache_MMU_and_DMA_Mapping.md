## 本课目标

沿一帧图像进入内存并交给 CPU 的过程，解释 DMA 的职责、CPU/设备地址差异，以及“传输完成、数据可见、允许访问”三个独立条件。

## 1. DMA 负责搬运，CPU 负责组织与接管

直接内存访问（Direct Memory Access，DMA）让硬件在配置后执行数据搬运，减少 CPU 逐字节读写的负担。
DMA 不一定是一颗独立芯片，也不一定是单独的通用控制器；采集或处理模块可集成内存写入逻辑。
CPU 仍要组织 Buffer、准备映射和参数、启动/排队、处理完成或错误，并管理复用与释放。

以下为典型 Camera 功能数据链，用于区分职责，不代表具体平台的处理顺序或物理连接。省略时钟/电源、格式转换、互联细节、缓存层级与多级队列：

```text
Sensor 产生图像数据
  → CSI 接收及可选处理模块
  → DMA/内存写入通路
  → 内存中的图像 Buffer
  → 完成必要交接后，CPU/软件读取或交给下游
```

Sensor 在此方案中负责输出数据；将它写入 SoC 内存的是接收/处理侧的 DMA 或内存写入通路。
它与读取 Sensor 寄存器的 I2C/I3C 控制链不同。ISP 可以在写内存之前或之后等不同位置参与，不从上述简图推定真实布局。
智能眼镜如此，TWS 中音频接口与内存之间也可采用硬件搬运，但具体资源和拓扑另查目标平台。

## 2. 给 DMA 的地址，不能直接照抄 CPU 指针

延续 [S1-03](Address_Spaces_and_Mapping.md)，先识别访问主体：

| 地址 | 谁使用 | 用途 |
|---|---|---|
| CPU 虚拟地址（VA） | CPU 软件 | 在当前映射中访问 Buffer |
| CPU 物理地址（PA） | CPU 侧硬件地址视图 | 定位对应内存等资源 |
| DMA 地址 | 指定设备的 DMA 访问路径 | 配置该设备访问 Buffer，Linux 用 `dma_addr_t` 表示 |

MMU（Memory Management Unit，内存管理单元）用于 CPU 侧的地址转换和访问控制；IOMMU（Input/Output Memory Management Unit，输入输出内存管理单元）可为设备 DMA 提供地址转换与隔离。
设备侧输入地址在相关平台常称 IOVA（I/O Virtual Address），不等于 CPU 的 VA。设备不沿普通 CPU 指针的地址转换上下文取数据。
没有 IOMMU 的平台仍可能有设备地址窗口、总线偏移或寻址范围限制；DMA 地址和 CPU PA 是否数值相同要查平台，不能假定。[Linux v6.8 CPU 与 DMA 地址](https://www.kernel.org/doc/html/v6.8/core-api/dma-api-howto.html)

用符号 V、P、D 表示某块 Buffer 的三个视图，仅用于教学：CPU 用 V，CPU 侧映射对应 P，设备按其有效映射使用 D。三者可能对应同一块内存，但未必数值相等。
IOMMU 映射正确也不自动解决 Cache 一致性、设备是否完成或 Buffer 是否已被释放。

## 3. Cache 为什么可能留下旧图像

缓存（Cache）保存靠近 CPU 的数据副本，以减少访问较远存储的开销。缓存行（Cache Line）是其管理粒度，不是任意一个软件变量或一帧图像。
写回式缓存中，CPU 修改后的数据可暂留在缓存行，称为脏数据（Dirty Data）；它与下层存储的内容可能暂时不同。

假设本例满足：

- CPU 可以缓存此 Buffer，且先前读到过旧帧 A。
- 设备 DMA 与 CPU Cache 不具备自动一致性。
- DMA 已按正确地址写完新帧 B，CPU 尚未进行所需的数据交接。

此时可出现：

| 观察位置 | 内容 |
|---|---|
| 内存中的目标数据 | 新帧 B |
| CPU Cache 中仍有效的旧副本 | 旧帧 A |
| CPU 直接读取且命中该副本 | 仍可能看到 A |

这说明“硬件已经写完”和“CPU 这次读取看到新值”不是同一条件；它不证明任何实际平台都存在此问题，也不意味着所有 DMA 写入都绕过全部缓存。
反方向也存在风险：CPU 准备发送数据，但更新只在 Cache 中，非一致性的设备可能读到下层旧值。[Arm 对软件/硬件一致性的说明](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/exploring-how-cache-coherency-accelerates-heterogeneous-compute)

## 4. Clean、Invalidate 与一致性不是万能修复

| 概念 | 本课中的机制含义 | 不能据此推定 |
|---|---|---|
| Clean / Write-back | 将脏缓存内容按架构规则写回到所需的一致性位置/存储层级 | 不自动等于设备工作完成或内存已可被并发修改 |
| Invalidate | 使指定缓存副本失效，让后续访问不再使用这个副本 | 不自动保留其中尚未写回的脏数据 |
| Hardware Coherency | 对配置正确且位于其一致性范围内的访问，硬件帮助维持数据视图一致 | 不自动保证操作顺序、请求完成和 Buffer 生命周期正确 |

这些是机制概念，不是对任意平台可直接调用的指令配方。“Flush”在不同接口中可能含义不同，应查实际定义。
如果设备已经写入新数据，再错误地将 CPU 的旧脏数据写回同一区域，可能覆盖新数据；对含有其他有效脏数据的范围盲目失效，也可能造成丢失。
缓存维护还涉及整行粒度，不能让不同拥有者随意共享同一缓存行后分别维护。实际范围、对齐和步骤由内存分配、平台及 DMA API 契约共同决定，不编造通用行大小或“完成后刷整个 Cache”的方案。

Linux 驱动应使用所属子系统与 DMA API 管理这些关系，不凭上述概念自行插入架构缓存指令。[Linux v6.8 DMA API 与缓存行约束](https://www.kernel.org/doc/html/v6.8/core-api/dma-api.html)

## 5. Buffer 所有权：谁现在可以访问或复用

本课的所有权（Ownership）指访问和复用的协议边界，不等于物理地址归属。
以下设定为同一图像区域交替由设备写入和 CPU 读取，未经特别分区或同步协议，不允许 CPU 在设备写入期间读取/修改该区域，也不允许设备覆盖 CPU 尚在处理的数据。

```text
CPU/框架准备 Buffer
  → 按协议映射、同步并交给设备
  → 设备写入，CPU 不擅自访问该区域
  → 确认本次传输完成且没有影响结果的错误
  → 完成面向 CPU 的必要同步与所有权交接
  → CPU/下游使用
  → 使用者归还，再按设备侧要求准备复用
```

硬件完成只是允许开始接管的条件之一，不代表 CPU 已处理完或所有下游消费者都归还了 Buffer。
双/多 Buffer 可让设备写下一块、CPU 处理上一块；仍需逐块维护状态，不会自动消除竞争。
超时也不能直接当作“设备已经停止”：取消、停止或恢复后，必须按硬件契约确认不会再访问该内存，才可撤销映射、释放或复用。

### 旧缓存副本与提前复用是两个问题

| 情景 | 具体机制与可能现象 | 应检查的条件 |
|---|---|---|
| 非一致性 Cache 中仍有旧副本 | 设备已写完新帧 B，CPU 却仍命中 A 的旧缓存副本 | 在 CPU 合法接管时，是否按 DMA/框架契约完成必要同步 |
| CPU 读 A 时设备已开始写 B | 同一区域仍在变化，CPU 可能读到混合两帧的内容或不稳定数据 | 所有使用者是否归还、是否过早重新排队；缓存一致性不能替代这个使用协议 |

第二种风险即使在缓存一致的平台上也存在：一致性不提供“整帧处理期间的数据快照”。不能仅用“CPU 读到旧帧”概括其原因，也不能靠一次缓存维护阻止后续覆盖。

在本课交替使用模型中，把交接顺序具体化：确认本轮设备完成且无影响结果的错误 → 必要同步并交 CPU → CPU/下游使用 → 所有使用者归还 → 完成设备侧必要准备 → 再次排队。
CPU 尚未用完时，应让设备使用另一块已经可用的 Buffer，或按实际队列协议等待/处理资源不足；不能直接覆盖仍被使用的区域。
复杂处理安排到合适线程上下文，与 Buffer 归还条件分别设计；把工作放进线程并不自动使 Buffer 可以立即复用。

## 6. Linux v6.8：两类接口与方向

下面只辨认 API 契约，不提供可复制的驱动流程，也不假设 Camera 框架把这些操作都交给当前这一层代码。

| 类型 | 入门用途与边界 |
|---|---|
| Coherent 分配，如 `dma_alloc_coherent()` | 获得 CPU 访问指针和设备使用的 DMA 地址；解决该分配契约内的缓存可见性，但仍需遵守顺序、同步和生命周期规则 |
| Streaming 映射，如 `dma_map_single()` | 将符合接口要求的已有 Buffer 映射给指定设备；检查映射结果，按正确方向在 CPU/设备之间交接，并匹配撤销 |

映射不只是地址数值转换，平台可能还执行必要缓存维护、IOMMU 设置或中转缓冲处理。CPU 的任意指针、栈内存或随意一段虚拟连续区域不能直接作为 `dma_map_single()` 的合法输入；内存来源及连续性等条件按接口核对。

方向以设备传输与内存之间的关系定义：

| Linux 方向 | 数据方向 | 典型用途 |
|---|---|---|
| `DMA_FROM_DEVICE` | 设备写到内存 | 本课图像采集示例，CPU 随后只读取 |
| `DMA_TO_DEVICE` | 内存供设备读取 | CPU 准备的数据交设备消费 |
| `DMA_BIDIRECTIONAL` | 两边可能修改 | 按双向契约处理，不能用它替代对实际读写的分析 |

保留 streaming 映射且在多次传输间让 CPU 访问时，通常通过对应的 `dma_sync_*_for_cpu()` / `dma_sync_*_for_device()` 完成交接；是否需要实际缓存操作由平台和方向契约决定。最后一次使用后按原设备、长度、方向及映射结果匹配撤销。
一次传输后结束映射可走匹配的 unmap 路径；不能把所有方案都写成“先 sync 再 unmap”的固定组合。
上述接口不代替等待硬件完成；CPU 接管后是否能写该区域也受映射方向约束，不能在 `DMA_FROM_DEVICE` 的接收示例中任意修改数据。
已经由 Buffer 框架负责的分配、映射和同步，应沿其契约使用，不能在上层盲目重复处理。[Linux v6.8 DMA 映射、方向与同步](https://www.kernel.org/doc/html/v6.8/core-api/dma-api.html)

## 7. 完成中断之后，CPU 读取前确认什么

| 要确认的条件 | 观测证据/依据 |
|---|---|
| 当前设备能访问这块内存 | 对应设备的有效 DMA 映射、地址范围、长度、权限和有效期 |
| 是本轮目标写入阶段完成 | 请求/Buffer 标识、完成语义、实际长度/范围及错误状态，而非其他阶段或旧事件 |
| 必要的数据同步与交接已完成 | 所属框架或 DMA API 的调用位置、参数及所有权状态 |
| Buffer 仍有效且未被下一轮覆盖 | 排队、完成、使用、归还与释放记录 |
| CPU 处理处于合适上下文 | 硬中断只做合适的即时处理；可能睡眠操作、整帧耗时处理安排到允许的线程上下文 |

仅有完成 IRQ、一个内存屏障、`volatile`、固定延时或 IOMMU 映射成功，都不能单独替代这组条件。屏障约束其定义的访问顺序，不会自动修复旧缓存副本、错误地址或提前复用。
硬中断限制复习见 [S1-06](Interrupts_and_Polling.md#4-处理上下文决定能做什么)。不把本表误读为任何 DMA API 都不能在硬中断调用；各接口按自身契约核对。

## 8. 工程锚点：完成通知到了，CPU 却读到旧帧或混帧

类型：模拟教学问题；无实际平台、实验结果或已确认根因。

已知仅为收到某项完成通知且 CPU 读到的图像不符合预期。是否目标写入阶段真正完成、地址是否对应、Cache 是否非一致、是否发生复用，都待核对。

| 待验证分支 | 优先验证动作 | 能缩小的范围 |
|---|---|---|
| 地址/长度不对应，或映射失效 | 关联同一请求的 CPU Buffer 标识、设备 DMA 地址、映射设备、长度与生命周期 | 是否实际写到了预期对象和范围 |
| 通知不是本轮内存写入完成 | 核对事件定义、Buffer 标识、实际写入范围及错误 | 排除旧事件、不同阶段或部分完成 |
| 缺少正确的数据交接 | 核对一致性属性、DMA 方向、框架同步位置及完整范围 | 非一致性条件下是否仍使用旧缓存副本；不能只凭现象断言 Cache 是根因 |
| CPU 尚在使用就被覆盖 | 关联设备开始写、完成、CPU 使用、下游归还与重新排队时间 | 定位提前复用或并发访问的可能性 |
| 格式/解释不匹配 | 按实际图像协议核对格式、stride、布局和解析位置 | 排除把布局或数据内容问题误判成缓存问题 |

记录符号或框架标识即可建立教学证据链，不虚构真实地址/参数。调试读取也要发生在允许访问 Buffer 的时机；不能为打印图像而破坏所有权。
当前没有定位结论；若证据确认某分支，再选择修正映射/长度、完成判据、同步契约或复用协议等措施。不能用全局关 Cache 或盲加延时作为已经验证的通用修复。
