## 本课目标

能解释硬件事件如何经轮询或中断被软件发现，并从状态、通知、处理与回调四个阶段定位“硬件有状态但软件没收到结果”的问题。

## 1. 轮询是主动查询，中断是事件通知

轮询（Polling）：软件再次读取状态，判断目标条件是否成立。
中断请求（Interrupt Request，IRQ）：硬件通过中断机制请求 CPU 处理事件；CPU 随后按平台和操作系统规则执行相应处理代码。

本课用一个假设模型比较：设备有可读取的原始完成状态 DONE，置位后会保持到按规则清除；读取没有副作用，设备中断使能只控制通知，不阻止工作或 DONE 置位。
这是本例明确条件；真实芯片可能有原始/屏蔽后状态之分，也可能存在读清除、脉冲状态或其他语义，必须核对手册。

| 比较点 | 轮询 | 中断 |
|---|---|---|
| 如何发现事件 | 软件再次检查状态 | IRQ 被送达并由处理代码识别事件 |
| 等待期间 | 可忙等，也可在允许睡眠的上下文中间隔检查 | 等待线程可阻塞，CPU 可运行其他任务；能否休眠还取决于系统条件 |
| 代价 | 状态读取与等待开销，检查间隔影响发现时间 | 中断进入、处理、调度及并发管理开销 |
| 主要前提 | 状态可安全读取、事件能被所选查询方式捕获 | 中断源、使能、路由、CPU 接收与软件处理链均正确 |
| 共同要求 | 确认本轮事件、区分完成和错误、设置合理超时 | 确认本轮事件、区分完成和错误、设置合理超时 |

忙等会持续占用执行资源；间隔查询可能引入发现延迟，且所选间隔可能漏掉未锁存的短暂状态。
短时间、受控场景可能选择轮询；较长或不确定等待可考虑事件通知。高频事件中逐次中断也可能昂贵，不把某种方式当作永远更快或更省电。
Linux 的忙等与睡眠接口有上下文限制，不能仅凭延时长短随意替换。[Linux v6.8 延时与睡眠说明](https://www.kernel.org/doc/html/v6.8/timers/timers-howto.html)

## 2. 硬件状态和 IRQ 不是一回事

假设一项采集任务执行到手册定义的完成阶段：

```text
硬件事件发生
  → 设备记录状态
  → 满足设备中断使能/输出条件
  → 中断控制器按配置送达 CPU
  → CPU/内核分派到驱动处理函数
  → 驱动确认事件并通知等待方或安排后续处理
  → 满足框架契约后，上层获得结果/回调
```

这是典型 SoC 的逻辑通知链，不是某芯片的布线图；省略桥接、级联中断域、跨处理器通信等结构。
中断可能来自 SoC 内部模块，不一定经过外部引脚。这里的“中断控制器”负责管理与分派 IRQ，与上一课执行 I2C 事务的控制器承担不同职责。
Linux 的通用 IRQ 层区分驱动接口、IRQ 处理流程和中断控制器硬件操作。[Linux v6.8 Generic IRQ](https://www.kernel.org/doc/html/v6.8/core-api/genericirq.html)

在本课假设中，设备 IRQ 关闭时 DONE 仍可为 1，轮询可以发现它；这与没有中断处理函数执行并不矛盾。
反过来，中断处理函数被调用也不能单凭这一点认定任务成功：中断可能来自错误、其他事件或共享中断线上的其他设备。需要识别来源和原因，再按本次任务条件处理。

## 3. 从硬件事件到回调，中间还有软件

中断服务例程（Interrupt Service Routine，ISR）是处理事件的程序，其具体动作由软件实现决定。中断通知本身不会搬运整帧图像，也不会天然生成上层 Camera 回调。
图像数据搬运由哪条硬件/软件路径完成属于下一课；本课只说明通知如何进入软件。

以下为典型分工，不规定所有工作都必须位于同一处理函数或采用同一清除顺序：

| 阶段 | 软件动作 | 观测点 |
|---|---|---|
| 事件识别 | 在允许的时机读取并保存必要状态，区分来源、完成、错误 | 本次状态快照与处理分支 |
| 设备侧处理 | 按手册清除/确认/屏蔽事件，避免丢事件或重复触发 | 合法的设备状态与使能信息 |
| 发布结果 | 更新受同步保护的任务结果，唤醒等待方或安排后续工作 | 请求标识、状态更新、通知/入队记录 |
| 后续执行 | 线程、普通工作队列或框架处理任务结果 | 是否实际执行、是否受阻、执行时使用的请求和数据 |
| 上层通知 | 满足接口契约后交付结果或错误 | 回调条件、回调目标和调用记录 |

IRQ/ISR 次数与帧数不保证一一对应：多个事件可能合并通知，一次 IRQ 也可能包含多种原因。
不能用一次 ISR 入口日志替代事件识别、当前请求匹配与回调完成的证据。

## 4. 处理上下文决定能做什么

处理上下文（Execution Context）描述代码在什么执行条件下运行，例如能否睡眠、阻塞、被调度，以及可以使用哪些同步接口。
本节专指 Linux v6.8 的常规硬中断与线程处理模型；其他 RTOS、裸机或特殊内核配置按其规则理解。

- 硬中断处理部分应短小，完成必要的即时处理；不能调用可能睡眠的接口，也不应在这里长时间等待、处理整帧图像或执行不受控的复杂工作。
- 需要允许阻塞的处理可选择线程化中断的线程部分，或普通线程工作队列等合适上下文，同时遵守所持锁和 API 的约束。
- “延后处理”本身不保证可以睡眠，必须确认实际机制与执行上下文，不能只看函数名或它发生在 ISR 之后。

Linux `request_threaded_irq()` 区分主处理函数与线程函数；它们的上下文不同。注册后处理函数就可能被调用，初始化与开启中断的时机需要协同设计。[Linux 线程化 IRQ 接口](https://www.kernel.org/doc/html/v6.8/core-api/genericirq.html)
普通线程工作队列将工作交给工作线程执行，但工作排入队列不等于工作已执行完成。[Linux v6.8 Workqueue](https://www.kernel.org/doc/html/v6.8/core-api/workqueue.html)

例如，普通同步 I2C 访问可能等待传输完成，不能直接放进要求不睡眠的硬中断路径；上一课的 API 返回语义不能替代这里的上下文检查。

## 5. 清设备事件、屏蔽 IRQ 和控制器确认要分开

| 动作 | 作用边界 |
|---|---|
| 清除设备事件状态 | 按设备规则消除记录或使事件源不再保持有效 |
| 屏蔽中断（Mask） | 在指定层级阻止通知送达；不自动等同于清状态或停止任务 |
| 中断控制器确认/EOI | 更新控制器接收和处理 IRQ 的状态；不自动清除外设内部状态 |

EOI（End Of Interrupt，中断结束通知）是某些控制器处理流程的一部分，不是所有驱动都应手工执行的通用动作。[Linux IRQ 控制器操作与流程](https://www.kernel.org/doc/html/v6.8/core-api/genericirq.html)

电平触发（Level-triggered）关注有效电平，边沿触发（Edge-triggered）关注规定方向的变化。具体保持、锁存、屏蔽期间是否保留、重新使能后如何重送，须查平台。
若电平型中断的设备源一直保持有效，单做控制器 EOI 可能再次进入处理，引发持续中断；这只是待验证分支，不能把所有重复 IRQ 都归因于漏清状态。

设备 W1C/读后清除规则见 [S1-04](Registers_and_MMIO.md#5-读写语义决定这个值是什么意思)。不重复读取带副作用的寄存器来“确认一下”；可以记录合法读取时保存的快照。
也不规定统一的“先清状态再开中断”配方：初始化、清旧状态、准备本轮等待、使能与启动的实际顺序须符合硬件协议并避免竞态。

## 6. 等待本轮完成，必须有条件与超时

轮询可用以下逻辑理解，属于伪代码，不提供可直接运行的寄存器访问或平台等待接口：

```text
按安全语义取得本轮状态快照
  → 若有错误，走失败处理
  → 若满足本轮完成条件，交付结果
  → 若达到期限，走超时与恢复
  → 否则按上下文允许的方式等待，再检查
```

固定等待一段时间只证明时间经过，不能单独证明任务完成。
中断方案也要等待一个与本轮任务关联的条件，并定义超时/错误处理；不能假设通知永远送达。

Linux completion 是一种等待/通知同步机制：应先初始化，之后通知可以早于等待到来；阻塞等待只能用于允许睡眠的上下文。它不自动判断硬件事件属于哪一轮任务。[Linux v6.8 Completions](https://www.kernel.org/doc/html/v6.8/scheduler/completion.html)
复用等待对象时需防止旧事件、错误重置或并发处理导致误判；超时后也要处理仍可能到来的完成，保证对象有效并与后续任务区分。这里不提供通用的 reset/start/wait 顺序代码。

在智能眼镜 Camera 中，应区分 Sensor 帧边界、接收模块完成、内存写入完成和软件 Buffer 交付；它们的名称即使都含 DONE，也不能不查定义就视为同一阶段。
TWS 音频数据准备/处理通知也有相同分层思路，但具体音频 IRQ 和数据通路不在本课预设。
收到中断不自动满足下一课讨论的 DMA/Cache 与内存可见性条件。

## 7. 工程锚点：状态置位，但没有 Camera 回调

类型：模拟教学问题。假设已通过合法读取确认本次设备状态满足预期事件条件，但上层没有收到回调；尚无真实平台、实验结果或已确认根因。

| 待验证阶段 | 检查与观测 | 若观察成立，下一步查什么 |
|---|---|---|
| 状态与任务对应 | 状态定义、错误位、请求标识及时间；排除旧 DONE 或不同阶段事件 | 确认该事件是否应该引出目标回调 |
| 设备通知 | 对应中断源使能、屏蔽及输出条件 | 设备是否产生预期 IRQ 请求 |
| IRQ 送达与分派 | 中断控制器配置、路由/触发类型/屏蔽、目标 CPU 接收条件、处理函数注册与计数 | 是否进入正确设备的处理代码 |
| 驱动事件处理 | 保存的状态快照、事件分支、请求匹配、结果发布与通知记录 | 是否通知了正确的等待方或安排后续工作 |
| 后续任务与框架 | 入队和执行分别记录，检查等待/锁/调度及框架回调条件 | 是否有任务受阻、错误过滤或回调对象不匹配 |

“IRQ 计数增加”只缩小到了通知/处理入口附近；共享 IRQ 下还需识别本设备来源，不能直接跳到“回调已执行”。
验证按证据逐层推进；不因为没回调就重启 Sensor，也不通过无依据增加固定延时来宣布修复。
当前没有实际实验结果，修复措施仅按验证出的分支选择：修正配置、按语义处理事件、修正同步或后续执行链。
关联 [Bring-up 方法](../09_Debugging_Bringup/README.md) 与 [Camera 模块](../05_Camera/README.md)。

### ISR 已执行之后，先检查哪两段软件

先限定：已经确认本次完成状态，且正确设备的 ISR 确实执行。此时继续沿软件链验证，不能把 ISR 入口等同于结果已交付。

| 检查环节 | 具体要确认什么 | 可增加的观测证据 |
|---|---|---|
| 驱动是否正确发布结果并发出后续通知 | 是否走到本次完成分支，更新了对应请求的结果；是否通知正确等待方或实际安排后续工作 | 同一请求标识下的事件类型、结果更新、通知对象及后续工作安排记录；仅有 ISR 入口不够 |
| 后续任务是否执行并走到回调条件 | 工作线程是否进入、是否被锁或等待阻塞，框架是否因错误、取消或请求不匹配而未走回调 | 同一请求标识下的任务入口/退出、等待前后，以及回调前的条件、分支和实际调用记录 |

以上是观测位置和待验证分支，没有实际测量时不能宣布根因。某些驱动直接通知等待方，另一些安排工作线程，不要求所有平台同时采用这两种方式。

例如，假设某驱动采用工作线程处理同一请求 R：

```text
R：ISR 识别本次完成
  → R：结果已更新，后续工作已确认排队
  → R：工作线程进入
  → R：回调前检查
  → R：实际调用回调
```

这是教学日志链，不是已有实验结果，也不是实际 API 名称。若只看到“已排队”，在排除日志缺失后仍需验证工作是否实际被调度执行；若工作已进入但没有回调，则继续检查线程内部等待和回调分支。
排队、执行和回调分别留证据，并用请求标识与时间关联，才能缩小问题范围。[Linux v6.8 Workqueue](https://www.kernel.org/doc/html/v6.8/core-api/workqueue.html)

## 8. 理解检查

1. 在本课假设中，DONE 是读取无副作用的锁存状态，中断使能只控制通知。设备 IRQ 关闭时，DONE=1 但 ISR 没有执行，是否矛盾？轮询能否发现完成？
2. Linux 常规硬中断处理函数里，为什么不应直接调用可能睡眠的同步 I2C 传输，或执行整帧图像处理？可把这类工作安排到哪里，还需确认什么？
3. 已确认本次完成状态，且正确设备的 ISR 已执行，但上层仍无回调。接下来检查哪两处软件环节？各举一项可观察证据。
